# rdpkey

Утилита проброса горячих клавиш в RDP-сеанс работодателя. Продолжение проекта `rdp-app`; сборка — `build.cmd` → `builds\rdpkey.exe`. Релизы на GitHub (`github`) и Gitverse (`origin`).

## Ложные срабатывания Microsoft Defender

`rdpkey.exe` периодически ловит **ложное срабатывание** — `Trojan:Win32/Wacatac.C!ml` (generic ML-эвристика облака Defender, типичный FP на небольших нестандартных бинарях). Чтобы сбить эвристику на этапе сборки, в `build.cmd` крутится сид `-randlayout <N>` после каждого обновления ML-модели Defender.

**Как лечить FP:**

1. Засабмитить файл на WDSI: https://www.microsoft.com/en-us/wdsi/filesubmission (consumer submission).
2. Дождаться **Final determination = `Not malware`** — значит Microsoft признал файл чистым и выкатывает корректирующее правило в cloud protection.
3. Проверять снятие: кнопка **Rescan submission** на WDSI + прогон хеша через VirusTotal (движок **Microsoft** на VT возвращает тот же облачный вердикт).

**Как это работает и сроки:**

- Облачный вердикт **динамический**, это не файл определений: Defender шлёт метаданные/хеш в облако, ответ malware / not-a-threat приходит в реальном времени. Поэтому `!ml`-детекты гаснут **без** обновления клиентских баз.
- В момент сабмита строка **Cloud** ещё может держать старый вердикт (`Online`), пока правило не докатилось до фронта облака.
- Распространение: без SLA, обычно час-два, иногда до суток. Правка **глобальная — на всех** через cloud protection.

**Важный подвох:** очистка привязана к **конкретному хешу**. После пересборки (новый `-randlayout` сид → новый хеш) ML-модель снова видит незнакомый бинарь и может опять влепить `Wacatac.C!ml`. Очистка **не переносится** на будущие билды. Поэтому после каждого релизного билда: прогнать хеш через VirusTotal → если Microsoft флагует, сразу слать FP-репорт на WDSI.
