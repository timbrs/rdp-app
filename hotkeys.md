# Метод перехвата клавиш в rdpkey

Документ описывает, **что** перехватывается, **как** устроен перехват, и —
главное — **что в нём можно ограничить, а что нельзя** и почему.

Всё описанное реализовано в `src/rdpkey.cpp`, функции `HookProc` / `Handle`.

## 1. Что перехватывается

Ровно пять позиций:

| Сочетание | Что уходит в сеанс |
|---|---|
| `Win` (нажать и отпустить) | тап по `Win` → удалённый Пуск |
| `Win + <клавиша>` | Win-аккорд с этой клавишей (добавочные модификаторы в аккорд не входят) |
| `Alt+Tab` | переключение удалённых окон вперёд |
| `Alt+Shift+Tab` | переключение удалённых окон назад |
| `Ctrl+Esc` | удалённый Пуск |

Перехват действует **только** пока в фокусе полноэкранное окно класса
`RAIL_WINDOW` (RemoteApp-окно RDP-клиента). Во всех остальных случаях
сочетания достаются локальной Windows.

Всё, что не в таблице, — включая `Ctrl+C`, `Ctrl+Alt+Del`, `Ctrl+Shift+Esc`,
`Ctrl+Alt+Tab`, любые буквы, цифры, F-клавиши и стрелки — не трогается.

## 2. Как устроен перехват

### Механизм

Глобальный низкоуровневый хук клавиатуры `WH_KEYBOARD_LL`, поставленный из
процесса `rdpkey.exe` (`SetWindowsHookExW`, снимается при выходе). Инъекции
кода в чужой процесс нет: LL-хук по своей природе живёт в своём процессе,
Windows сама вызывает callback в его потоке.

Решение по каждому событию — двоичное:

- `return 1` из `HookProc` — событие **проглочено**, до локальной Windows и
  до приложений не доходит;
- `CallNextHookEx` — событие идёт дальше нетронутым.

Доставка в сеанс — не через `SendInput` (он бы вернулся в тот же хук и в
локальную систему), а `PostMessageW` в окно класса `IHWindowClass` внутри
процесса `mstsc` (`PostSeq`). Это межпроцессная отправка сообщения, не
инъекция.

### Провод

Последовательность собирается по **скан-кодам** (`struct Scan`), потому что
`mstscax` фильтрует часть сочетаний по vk:

- `Win` идёт со скан-кодом `0x5B`, но vk `0x41` (`WIN_WIRE_VK`) — обход
  фильтра Win-клавиши;
- `Tab` в `Alt+Tab` шлётся флагом `noSys` — как `WM_KEYDOWN`, а не
  `WM_SYSKEYDOWN`, в обход фильтра Alt+Tab.

Для `Alt+Tab` в режиме `tab` (`g_altMode`) `Alt` вообще не шлётся: удалённой
стороне достаточно самих `Tab`. Механика «sticky»-модификаторов
(`s_altSticky`, `s_shiftSticky`) существует для других режимов и снимается
при потере фокуса (`ReleaseSticky`).

### Порядок фильтров в `Handle()`

Важен именно порядок — он определяет, сколько работы делается над
посторонней клавишей.

1. **`LLKHF_INJECTED`** → выход. Отсекает синтетический ввод, в том числе
   защищает от петли обратной связи.
2. **Не key-down и не key-up** → выход.
3. **Синхронизация `s_winDown` с железом.** `Win` мог быть отпущен, пока
   фокус был вне сессии; залипший флаг иначе глотал бы посторонние клавиши.
   События самой Win-клавиши из сверки исключены: на её up
   `GetAsyncKeyState` уже показывает «отпущена» (асинхронное состояние
   обновляется до вызова хука), и сброс здесь съел бы тап по `Win`.
4. **`IsWatchedKey(vk)`** → выход, если клавиша не из списка `Win`, `Alt`,
   `Shift`, `Tab`, `Esc` (исключение: пока `Win` зажат, в аккорд идёт любая
   клавиша — это явное намерение пользователя).
5. Только теперь читаются `scanCode` и `LLKHF_EXTENDED`.
6. **`IsRemoteFocused()`** — `GetForegroundWindow` → класс `RAIL_WINDOW` →
   полный экран (`GetWindowRect` + `MonitorFromWindow`) → наличие
   `IHWindowClass` (`FindIHWindow`, с кэшем по PID). Не тот фокус — снять
   sticky и выйти.
7. Ветки сочетаний со **строгой** маской модификаторов (`ModMask`): набор
   зажатых модификаторов должен совпадать точно, а не «содержать нужный».

Практический эффект шага 4: для любой посторонней клавиши путь исполнения =
один `switch` по `vkCode` и `return false`. Ни одного вызова WinAPI, без
чтения скан-кода, без записи состояния.

### Строгие маски

- Win-аккорд: чистые модификаторы (`Ctrl`, `Alt`, `Shift`, `Win`) исключены
  из аккорда, чтобы `Win+Ctrl` сам по себе не порождал ложную посылку.
  Следствие: добавочный модификатор в аккорд не попадает — `Win+Shift+S`
  уходит в сеанс как `Win+S`. Ветки `Alt`/`Shift` стоят раньше ветки аккорда
  и возвращают событие хосту.
- `Alt+Tab`: маска ровно `ALT` либо `ALT|SHIFT`. Поэтому `Ctrl+Alt+Tab`
  уходит хосту.
- `Ctrl+Esc`: маска ровно `CTRL`. Поэтому `Ctrl+Shift+Esc` (диспетчер задач)
  уходит хосту.

### Симметрия up-событий

Маска проверяется одинаково для down и up. `Tab`-up приходит при всё ещё
зажатом `Alt` → маска совпадает → событие глушится так же, как down.
Аналогично `Esc`-up при зажатом `Ctrl`. Асимметрии «down проглотили, up
утёк» не возникает — иначе приложение получило бы непарный up.

## 3. Что можно ограничить

Всё перечисленное — уже реализовано либо доступно правкой одной строки.

| Ограничение | Как | Состояние |
|---|---|---|
| Набор клавиш, над которыми вообще выполняется работа | `IsWatchedKey` | сделано |
| Точный набор модификаторов | `ModMask` + сравнение на равенство | сделано |
| Условие фокуса: только полноэкранное `RAIL_WINDOW` | `IsRemoteFocused` | сделано |
| Игнор синтетического ввода | `LLKHF_INJECTED` | сделано |
| Время жизни хука: только пока жива сессия | `SetWindowsHookExW` / `UnhookWindowsHookEx`, счётчик `VisibleRailCount` | сделано |
| Отключение отдельных сочетаний | флаги `g_fwdWin`, `g_fwdWinCombo`, `g_fwdAltTab`, `g_fwdCtrlEsc` | правка константы |
| Отказ от Win-аккордов с произвольной клавишей | `g_fwdWinCombo = false` | правка константы |

**Что ещё можно ужесточить, но пока не сделано.** `IsRemoteFocused()`
принимает *любой* процесс с полноэкранным `RAIL_WINDOW` и дочерним
`IHWindowClass`, а не только тот сеанс, который поднял сам `rdpkey`. Сверка
`g_targetPid` с порождённым PID (`CreateProcessW` в `RunMode`) сузила бы цель
до единственного доверенного сеанса.

Оговорка: в лоб это не заработает — `mstsc` умеет передавать сеанс фоновому
`mstsc.exe -Embedding` (тот же механизм, из-за которого счёт живых сессий
ведётся по видимым `RAIL_WINDOW`, а не по процессам). Порождённый PID может
не совпадать с тем, что держит окно, поэтому сверку пришлось бы вести иначе —
например, по цепочке родителей или по времени создания процесса. Требует
проверки на живом сеансе.

## 4. Что ограничить нельзя

Это границы механизма, а не недоработка.

**Callback вызывается на каждое событие клавиатуры.** Свойство
`WH_KEYBOARD_LL`: подписки «только на Alt+Tab» не существует, фильтра по
клавише у API нет. Устранить это нельзя — можно только сократить объём
работы над нерелевантным событием, что и сделано (шаг 4 выше). Вызов
callback'а остаётся.

**`RegisterHotKey` вместо хука не подходит.** Она умеет узкую подписку, но
не берёт ни `Alt+Tab`, ни `Ctrl+Esc` (зарезервированы системой), ни
одиночный `Win`. То есть покрывает ноль из пяти нужных позиций.

**`Ctrl+Alt+Del` перехватить нельзя в принципе.** Secure Attention Sequence
обрабатывается ядром и `winlogon` до пользовательских хуков; событие до
`HookProc` не доходит. Это защита ОС, обходить её не следует.

**Защищённый рабочий стол недоступен.** Пока активен UAC-промпт, экран
блокировки или экран `Ctrl+Alt+Del`, ввод идёт на другой desktop — хук не
вызывается вообще.

**Окна с более высоким уровнем целостности недоступны.** `rdpkey` запущен
без повышения (`app.manifest`), поэтому когда в фокусе окно
elevated-процесса, UIPI не отдаёт хуку события. Для целевого сценария это
нормально и даже полезно: ввод в административные окна утилита не видит.

**Порядок среди других LL-хуков не контролируется.** Хуки вызываются по
цепочке в порядке установки; другая утилита может проглотить событие раньше.
Гарантий очерёдности API не даёт.

**Что доедет до удалённой стороны — решает `mstscax`.** Часть сочетаний он
фильтрует по vk и по alt-контексту; отсюда обходы `WIN_WIRE_VK` и `noSys`.
Это ограничение RDP-клиента, а не хука.

**Оконный режим вложенного RDP не поддерживается сознательно.** Фокусный
`RAIL_WINDOW` там относится не к тому слою, и сочетания ушли бы не на
целевую машину — поэтому требуется полный экран.

## 5. Границы приватности

Хук **видит** факт нажатия каждой клавиши (шаг 4 отсекает работу, но не сам
вызов). При этом:

- ввод никуда не сохраняется, не накапливается и не передаётся;
- для клавиш вне списка не читается даже скан-код, состояние не пишется;
- проглатывается (`return 1`) только то, что попало в целевые ветки при
  правильном фокусе; всё остальное идёт приложениям нетронутым;
- ввод в окна elevated-процессов и на защищённом рабочем столе недоступен
  утилите технически.
