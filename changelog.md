# Changelog

## 1.0.3

### Исправлены Win-аккорды (`Win+D`, `Win+E`, …)

Регрессия из 1.0.2. Симптом: `Win`-сочетания перехватывались (локально
ничего не срабатывало), но в сеанс не уходили; одиночный `Win` и `Alt+Tab`
работали.

#### Причина

Сверка залипшего `s_winDown` с состоянием клавиатуры опиралась на неверное
допущение о поведении Windows:

```cpp
if (s_winDown && !isWinKey && !IsDown(VK_LWIN) && !IsDown(VK_RWIN)) { s_winDown = false; ... }
```

`Win`-down мы глушим сами (`return true` из хука), а **заглушённая LL-хуком
клавиша асинхронное состояние не обновляет вовсе**. Поэтому
`GetAsyncKeyState(VK_LWIN)` возвращает ноль всё время, пока `Win` физически
зажат, и первая же клавиша аккорда сбрасывала `s_winDown`. Дальше срабатывал
фильтр `if (!s_winDown && !IsWatchedKey(vk)) return false;` — клавиша уходила
хосту, `SendWinChord()` не вызывался.

Почему остальное работало: одиночный `Win` — события Win-клавиши были
исключены из сверки; `Alt+Tab` — `Alt` хук не глушит, так что его
асинхронное состояние настоящее.

#### Измерено, а не выведено

Отдельная программа ставит LL-хук и логирует `GetAsyncKeyState(VK_LWIN)` на
каждом событии — два прогона, с глушением `Win` и без:

```
A. хук ГЛУШИТ Win            B. хук ПРОПУСКАЕТ Win (контроль)
  LWIN DOWN | async=0          LWIN DOWN | async=0
  F13  DOWN | async=0          F13  DOWN | async=1
  F13  UP   | async=0          F13  UP   | async=1
  LWIN UP   | async=0          LWIN UP   | async=1
```

Отсюда два факта. Первый: заглушённая клавиша состояние не обновляет (A) —
это и есть баг. Второй: состояние обновляется **после** возврата из хука, а
не до (B, строка `LWIN DOWN`) — то есть объяснение регрессии в разборе 1.0.2
было неверным, хотя сама правка (исключить события Win-клавиши) требовалась,
просто по другой причине.

#### Исправление

Состояние `Win` ведётся только по событиям хука. От залипания страхуют сброс
в ветке `!IsRemoteFocused()` (любая клавиша вне сеанса снимает флаг) и
таймаут `WIN_HOLD_MAX_MS = 30000` — удержание дольше означает потерянный
`up` (например, `Win` отпустили на секретном рабочем столе UAC, куда хук не
дотягивается).

```cpp
if (s_winDown && GetTickCount64() - s_winDownTick > WIN_HOLD_MAX_MS) { s_winDown = false; s_winCombo = false; }
```

Побочный эффект: на посторонней клавише при зажатом `Win` вместо двух
вызовов `GetAsyncKeyState` теперь одно чтение счётчика тиков.

Провод не менялся: `WIN_WIRE_VK = 0x41`, скан-коды и порядок сообщений
прежние.

#### Как проверено

Харнесс логики `Handle()` с подменёнными WinAPI, где модель поведения
Windows взята из измерений выше (заглушённая клавиша состояние не меняет).
14 сценариев: тап `Win`, два тапа подряд, правый `Win`, `Win+D`, `Win+E`,
`Win` с двумя клавишами подряд, автоповтор, `Alt+Tab`, `Ctrl+Esc`, обычная
печать, работа вне сеанса, потеря фокуса, залипший `Win` по таймауту,
легальное удержание 5 с. Сверялся точный провод `PostMessageW`.

Версия 1.0.2 на этом наборе даёт 6 провалов — все Win-аккорды с пустым
проводом, что воспроизводит жалобу. После правки 14/14 проходят.

Сборка `build.cmd` проходит; `-Wall -Wextra` даёт только предсуществующие
`-Wmissing-field-initializers`.

### Info-экран показывает версию

Запуск без аргументов теперь печатает `rdpkey 1.0.3 — проброс горячих клавиш
в RDP RemoteApp`.

Версия вынесена в `src/version.h` — единственный источник для обоих
потребителей, чтобы строка на экране и ресурс `VS_VERSION_INFO` не разъехались:

```c
#define RDPKEY_VER_NUM 1,0,3,0     // FILEVERSION/PRODUCTVERSION в ресурсе
#define RDPKEY_VER_STR "1.0.3.0"   // строковые поля ресурса
#define RDPKEY_VER     "1.0.3"     // то, что показывает info-экран
```

`rdpkey.rc` и `rdpkey.cpp` подключают его; `windres` находит заголовок по уже
имевшемуся `--include-dir src`, правок в `build.cmd` не потребовалось. При
выпуске правится только `version.h`.

## 1.0.2

Два изменения: сужение области перехвата и исправление пробоя одиночного
`Win`. Оба выходят одним релизом — теги `v1.0.0` и `v1.0.1` указывают на один
и тот же коммит `4936dfe`, то есть сужение области ранее не выпускалось.

### Исправлен пробой одиночного `Win`

Регрессия, внесённая сужением области (коммит `c0b6894`). Сверка залипшего
`s_winDown` с фактическим состоянием клавиш выполнялась для **всех** событий,
включая события самой Win-клавиши:

```cpp
if (s_winDown && !IsDown(VK_LWIN) && !IsDown(VK_RWIN)) { s_winDown = false; ... }
```

На событии **Win-up** `GetAsyncKeyState(VK_LWIN)` уже показывает «отпущена» —
асинхронное состояние клавиатуры обновляется до вызова LL-хука. Поэтому
`s_winDown` сбрасывался в `false` ещё до ветки, которая шлёт тап, и условие
`if (s_winDown && !s_winCombo) SendWinTap()` не срабатывало никогда.
Одиночный `Win` не открывал удалённый Пуск; `Win+<клавиша>` при этом работал,
так как там Win физически зажат в момент события.

> **Уточнение из 1.0.3.** Этот абзац неверен в двух местах, и измерения это
> показали. Асинхронное состояние обновляется *после* возврата из хука, а не
> до; заглушённая клавиша не обновляет его вообще. И `Win+<клавиша>` в 1.0.2
> как раз **не** работал — сверка ломала именно аккорды. Сама правка ниже
> нужна, но по другой причине.

Исправление: события самой Win-клавиши исключены из сверки.

```cpp
bool isWinKey = (vk == VK_LWIN || vk == VK_RWIN);
if (s_winDown && !isWinKey && !IsDown(VK_LWIN) && !IsDown(VK_RWIN)) { ... }
```

Защита от залипания сохранена: она срабатывает на первой же посторонней
клавише, когда `Win` физически не зажат.

Версия в `src/rdpkey.rc` поднята до `1.0.2.0` (оставалась `1.0.0.0` при
выпущенном `v1.0.1`).

#### Как проверено

Логика `Handle()` прогнана тестовым харнессом с подменёнными WinAPI
(`GetAsyncKeyState`, `PostMessageW`, окружение `IsRemoteFocused`) на 16
сценариях: тап `Win`, правый `Win`, два тапа подряд, `Win+E`, `Win+Ctrl`,
`Win+Ctrl+X`, `Win+Shift+S`, `Alt+Tab`, `Alt+Shift+Tab`, `Ctrl+Esc`,
`Ctrl+Shift+Esc`, `Ctrl+Alt+Tab`, обычная печать, залипание `Win`, потеря
фокуса, симметрия up-событий. Сверялся точный провод `PostMessageW`.

Версия из коммита `c0b6894` на сценарии «тап `Win`» даёт пустой провод —
регрессия воспроизведена; после правки 22/22 проверки проходят.

Прогон делался в двух моделях: async-состояние обновляется до вызова хука и
после него. Старая версия падает только в первой — что и подтверждает
реальное поведение Windows. Новая проходит в обеих, то есть от порядка
обновления не зависит.

#### Уточнение к документации

`Win+Shift+S` (и любой Win-аккорд с добавочным модификатором) уходит в сеанс
как `Win+S` — без `Shift`: ветка `Shift` стоит раньше ветки Win-аккорда и
возвращает `false`, поэтому модификатор в аккорд не попадает. Поведение
существовало и до правок этого релиза, но в описании было указано неверно.

### Сужена область перехвата клавиш в LL-хуке

Затронут `src/rdpkey.cpp`; `build.cmd` и `src/app.manifest` не менялись.

#### Проблема

`Handle()` **анализировал** каждое нажатие в системе: для любой буквы читал
`vkCode`/`scanCode`/`flags` и вызывал дорогую `IsRemoteFocused()`
(`GetForegroundWindow` → `GetClassNameA` → `GetWindowRect` →
`MonitorFromWindow` → `FindIHWindow`).

Уточнение: *глушились* при этом не все клавиши, а только те, что попадали в
целевые ветки (`return true`); остальные шли дальше через `CallNextHookEx` и
доходили до приложений нетронутыми. Никакого сохранения, накопления или
передачи ввода не было и нет. Проблема была в **области доступа**: утилита,
поставленная ради пяти сочетаний, читала данные каждого нажатия, включая
набираемые в посторонних приложениях пароли.

Вторая проблема: проверки модификаторов были нестрогими — хватало, чтобы
нужный модификатор был зажат. Из-за этого перехватывались сочетания, которых
нет в списке: `Ctrl+Alt+Tab` уходил в сеанс как `Alt+Tab`, а `Ctrl+Shift+Esc`
(диспетчер задач) — как `Ctrl+Esc`.

#### Что сделано

**Классификатор клавиш** (`IsWatchedKey`, `IsModifierKey`). Список клавиш,
участвующих в пробрасываемых сочетаниях: `Win`, `Alt`, `Shift`, `Tab`, `Esc`.

**Маска модификаторов** (`ModMask`) для строгого сравнения набора зажатых
модификаторов вместо проверок «зажат ли нужный». Переиспользована
существующая обёртка `IsDown` — новых обращений к `GetAsyncKeyState` нет.

**Ранний выход в `Handle()`.** После разбора `down`/`up` и до чтения
скан-кода:

```cpp
if (!s_winDown && !IsWatchedKey(vk)) return false;
```

`scanCode`/`flags` читаются и `IsRemoteFocused()` вызывается **после**
фильтра. Для нерелевантной клавиши путь исполнения = один `switch` по
`vkCode` и `return false`: ни одного вызова WinAPI, без чтения скан-кода, без
сохранения состояния.

Там же добавлена сверка залипшего `s_winDown` с фактическим состоянием
клавиш: `Win` мог быть отпущен, пока фокус был вне сессии, и залипший флаг
глотал бы посторонние клавиши.

**Строгие условия сочетаний:**

- Win-аккорд — чистые модификаторы (`Ctrl`, `Alt`, `Shift`, `Win`) исключены
  из аккорда и уходят хосту, чтобы `Win+Ctrl` сам по себе не порождал ложную
  посылку.
- `Alt+Tab` — маска ровно `ALT` либо `ALT|SHIFT`; `shift` берётся из уже
  вычисленной маски вместо повторного `IsDown(VK_SHIFT)`.
- `Ctrl+Esc` — маска ровно `CTRL`.

Ветки `Win` и модификаторов `Alt`/`Shift` оставлены как были — они нужны для
запоминания `s_altScan`/`s_shiftScan` и снятия sticky.

Функции отправки (`SendWinTap`, `SendWinChord`, `SendAltTab`,
`ReleaseSticky`, `PostSeq`, `MakeLParam`) и их сигнатуры не менялись — провод
байт-в-байт прежний, включая обходы фильтров `WIN_WIRE_VK = 0x41` и `noSys`
для `Tab`.

#### Отступление от плана

Имена `MOD_ALT`, `MOD_SHIFT`, `MOD_WIN` заняты макросами `winuser.h`
(константы для `RegisterHotKey`) — `enum { MOD_ALT = 1, ... }` не
компилировался. Префикс переименован в `KM_`; значения и логика те же.

#### Итоговое поведение

| Ввод | Результат |
|---|---|
| Любая буква/цифра/F-клавиша/стрелка | выход по `switch`, ноль вызовов WinAPI |
| `Ctrl`, `Ctrl+C`, `Ctrl+Alt+Del` | не в списке → хосту |
| `Win`, `Win+E` | перехват → в сеанс |
| `Win+Shift+S` | перехват → в сеанс как `Win+S`, без `Shift` |
| `Alt+Tab`, `Alt+Shift+Tab` | перехват → в сеанс |
| `Ctrl+Esc` | перехват → в сеанс |
| `Ctrl+Alt+Tab`, `Ctrl+Shift+Esc` | хосту, нетронутыми |
| `Win+Ctrl+X`, `Win+Alt+Tab` | Win-аккорд (Win зажат — явное намерение) |
| Всё перечисленное вне полноэкранного `RAIL_WINDOW` | хосту (`IsRemoteFocused`) |

#### Ограничение

Сам callback LL-хука Windows вызывает на все события клавиатуры — это
свойство `WH_KEYBOARD_LL`, устранить его нельзя. Альтернатива
`RegisterHotKey` не подходит: она не умеет ни `Alt+Tab`, ни `Ctrl+Esc`
(зарезервированы системой), ни одиночный `Win`. Сужено то, что хук *делает* с
событием.

#### Проверено

Сборка `build.cmd` проходит без warning'ов, `builds\rdpkey.exe` пересобран.
Дополнительный прогон с `-Wall -Wextra` даёт только предсуществующие
`-Wmissing-field-initializers` на агрегатной инициализации (`STARTUPINFOW`,
`Scan`) — к изменениям не относятся.

Ручные проверки в живом сеансе на этом этапе не выполнялись — из-за чего
пробой одиночного `Win` и всплыл только после установки. Исправление
покрыто тестовым харнессом (см. выше).
